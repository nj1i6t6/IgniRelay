# 烽傳 (IgniRelay) — 全台災難通訊骨幹網路架構設計文件

## 版本：v0.1 草案
## 日期：2026-03-14

---

## 一、設計理念

當 4G/5G 基地台、光纖、Wi-Fi 等傳統通訊基礎設施因地震、颱風、戰爭等極端事件全面癱瘓時，烽傳網路提供一套完全獨立於現有電信基礎設施的災難通訊骨幹。

核心原則：
- 零依賴：不依賴任何現有電信基礎設施即可獨立運作
- 容錯冗餘：任何單點故障不影響整體網路運作
- 對齊行政體系：通訊階層與台灣災害應變中心（EOC）分級指揮架構完全吻合
- 太陽能自持：所有節點具備太陽能供電，可長期無人值守運作
- 漸進部署：可依預算分階段建置，先覆蓋人口密集區再向外擴展

## 三、各層設備規格與功能

### 第二層：LoRa 骨幹節點（純 LoRa）

**用途：** 全台長距離資料傳輸主幹道，不直接與使用者互動。

**部署位置：** 山頂、高樓屋頂、電信鐵塔、高壓電塔（借用既有高點基礎設施）。

**技術規格：**
| 項目 | 規格 |
|------|------|
| 通訊模組 | LoRa SX1262，Coded PHY |
| 發射功率 | +20 dBm（法規上限） |
| 天線 | 高增益全向天線（8 dBi 以上） |
| 覆蓋半徑 | 平地 5-10km / 山頂對山頂 15-50km |
| 太陽能板 | 10W 單晶矽防水 |
| 電池 | 6× 18650（約 66 Wh，可撐 72+ 小時無日照） |
| 電源管理 | MPPT 太陽能充電控制 |
| 外殼 | IP67 防水防塵，耐候設計 |

**容錯佈陣原則：**
- 節點間距 = LoRa 有效覆蓋半徑 × 70%（非極限距離）
- 採用六角蜂巢式佈陣（非正方形九宮格，六角形覆蓋效率最高）
- 任意單一節點失效，其覆蓋範圍至少被 2 個相鄰節點覆蓋
- 關鍵路徑（如中央山脈稜線）額外增設冗餘節點

**單組成本估算：**
| 組件 | 估價（台幣） |
|------|------------|
| LoRa 模組 + MCU（ESP32-S3） | 700 |
| 高增益天線 | 400 |
| 太陽能板 10W | 450 |
| 電池組 6× 18650 | 750 |
| MPPT 控制板 | 200 |
| IP67 外殼 + 支架 | 700 |
| **合計** | **約 3,200 元** |

### 第三層：LoRa + BLE 複合中繼站

**用途：** BLE 網路與 LoRa 骨幹之間的橋樑。是整個系統中功能最關鍵的節點。

**部署位置：** 
- 縣市災害應變中心 / EOC
- 區公所 / 鄉鎮市公所
- 警察局（派出所、分局）
- 消防局（分隊、大隊）
- 醫院（區域醫院以上）
- 大型避難收容所（學校體育館、活動中心）
- 車站（台鐵、高鐵、捷運站出口）

**技術規格：**
| 項目 | 規格 |
|------|------|
| LoRa 模組 | SX1262 + 高增益天線 |
| BLE 模組 | nRF52840 含 PA/LNA（+20 dBm） |
| BLE 覆蓋 | 半徑 100-200m |
| MCU | ESP32-S3 或同等級 |
| 本地儲存 | 8-16GB SD 卡（暫存彙整資料） |
| 太陽能板 | 10W |
| 電池 | 6× 18650 |
| 外殼 | IP67 |

**核心功能：**
1. BLE 掃描：持續接收來自第四層 BLE 基地台和直接來自手機的資料
2. 資料彙整：去重（Bloom Filter）、壓縮（Protobuf）、優先排序（Triage Queue）
3. LoRa 上傳：定期將彙整摘要透過 LoRa 發送至骨幹網路
4. LoRa 下載：接收來自指揮中心的指令和資訊
5. BLE 廣播：將外界資訊透過 BLE 推送給範圍內的手機和 BLE 基地台

**資料彙整邏輯：**
```
每 N 分鐘（可動態調整）執行一次：
1. 收集 buffer 中所有來自 BLE 的事件
2. Bloom Filter 去重
3. 依 Triage 優先級排序：
   - P0：SOS_RED（生命危急）→ 立即送出，不等排程
   - P1：SOS_YELLOW（需要協助）→ 下一個排程週期
   - P2：RESOURCE（物資需求/供給）→ 正常排程
   - P3：INFO（一般資訊）→ 低優先級，頻寬有餘時才送
4. Protobuf 序列化壓縮
5. 透過 LoRa 送出
```

### 第四層：BLE 基地台（純 BLE）

**用途：** 最密集的末端收集網路，直接與使用者手機互動。

**部署位置：**
- 路燈（最理想：供電方便、高度適中、密度高）
- 電線桿
- 公車站牌
- 便利商店外牆
- 公共建築外牆（郵局、銀行、圖書館）
- 公園涼亭

**技術規格：**
| 項目 | 規格 |
|------|------|
| BLE 模組 | nRF52840 含 PA/LNA |
| 發射功率 | +20 dBm |
| BLE 覆蓋 | 半徑 100m（城市實際環境） |
| MCU | nRF52840 內建（不需額外 MCU） |
| 太陽能板 | 5-6W（功耗較低，不需要 LoRa） |
| 電池 | 3× 18650（約 33 Wh） |
| 外殼 | IP67，體積盡量小 |

**核心功能：**
1. BLE 掃描：接收手機 app 的 broadcast 資料
2. BLE 廣播：將收到的資料轉播出去（中繼功能）
3. BLE mesh relay：與相鄰的 BLE 基地台形成 mesh，將資料 hop 到最近的第三層中繼站

**關鍵部署原則：**
- 相鄰 BLE 基地台之間的距離 ≤ 150m（確保 100m 覆蓋半徑有重疊）
- 不能有斷層：從任何一個 BLE 基地台出發，必須能透過 BLE mesh hop 到至少一個第三層中繼站
- 部署密度隨人口密度遞減

**單組成本估算：**

| BLE 模組（nRF52840 + PA/LNA） | 500 |
| 天線 | 200 |
| 太陽能板 5W | 300 |
| 電池組 3× 18650 | 380 |
| MPPT 控制板 | 150 |
| IP67 小型外殼 + 支架 | 400 |

## 四、通訊流程

### 上行（使用者 → 指揮中心）

```
1. 用戶手機發送 SOS_RED broadcast
         ↓ BLE（100m）
2. 附近的 BLE 基地台收到
         ↓ BLE mesh relay（基地台之間 hop）
3. 資料到達最近的 LoRa+BLE 複合中繼站
         ↓ 彙整、去重、壓縮、Triage 排序
4. 透過 LoRa 發送至骨幹網路
         ↓ LoRa mesh hop（骨幹節點之間）
5. 到達縣市 EOC 的 LoRa 閘道
         ↓ LoRa 骨幹
6. 到達中央指揮中心
```

### 下行（指揮中心 → 使用者）

```
1. 指揮中心發布指令：「北區往南撤離，X 路段不通」
         ↓ LoRa 骨幹
2. 各縣市 EOC 收到
         ↓ LoRa
3. 各 LoRa+BLE 複合中繼站收到
         ↓ BLE broadcast（中繼站直接向周圍手機廣播）
         ↓ 同時透過 BLE mesh 推送至轄區內所有 BLE 基地台
4. BLE 基地台轉播
         ↓ BLE（100m）
5. 用戶手機收到指令
```

### 橫向（避難所 A ↔ 避難所 B）

```
避難所 A 手機群                              避難所 B 手機群
    ↓ BLE                                       ↑ BLE
BLE 基地台群                                 BLE 基地台群
    ↓ BLE mesh                                  ↑ BLE mesh
LoRa+BLE 中繼站 A ──── LoRa ────→ LoRa+BLE 中繼站 B
              （可能經過數個 LoRa 骨幹節點 hop）
```

## 八、LoRa 頻寬與容量規劃

### 單一 LoRa 節點容量
- 傳輸速率：約 300 bytes/秒（SF12, 125kHz, Coded PHY）
- Duty cycle 限制（台灣 ISM band）：約 1-10%
- 實際有效吞吐量：每小時約 1,000-2,000 則短訊息（50 bytes/則）

### 資料壓縮策略
一個避難所（500 人）的狀態摘要，經 Protobuf 壓縮後：
```
{
  shelter_id: 4 bytes
  gps: 8 bytes
  population: 2 bytes
  medical_urgent: 2 bytes
  needs: [water, blanket, medicine] → bitmap 4 bytes
  sos_red_count: 2 bytes
  timestamp: 8 bytes
  bloom_filter_hash: 16 bytes
}
≈ 50-100 bytes，一次 LoRa 傳輸即可完成
```

### 全網容量評估
假設全台 2,500 個 LoRa+BLE 中繼站，每個每 5 分鐘送一次 100 bytes 摘要：
- 每小時每站：12 次 × 100 bytes = 1,200 bytes
- 全網每小時：2,500 × 1,200 = 3 MB
- LoRa mesh 骨幹需要承載的流量：分散在 1,000 個骨幹節點上，每個節點每小時只需轉發約 3 KB
- 結論：LoRa 頻寬完全足夠

## 九、未來擴展方向

### 衛星回程（Satellite Backhaul）
在中央山脈稜線等無法用 LoRa hop 到平地的位置，部署 Starlink Mini 或 Iridium 終端，將 LoRa 骨幹資料透過衛星回傳指揮中心。

### 無人機中繼
在 LoRa 骨幹某段因災損中斷時，部署攜帶 LoRa 模組的無人機作為臨時中繼節點，恢復骨幹連通性。

### 業餘無線電整合
與台灣業餘無線電社群合作，將 Ham Radio Packet 作為 LoRa 骨幹的備援傳輸層。

### IgniMesh SDK
將 BLE 基地台的韌體邏輯封裝成 SDK，提供給其他硬體廠商整合到他們的設備中（如智慧路燈、環境監測站），擴大 BLE 覆蓋網路。
