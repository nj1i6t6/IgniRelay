# 專案分析與技術構思報告 (Project Analysis & Technical Ideation)
## 專案名稱：災難應急 Mesh 物資調度系統 (Project ResQMesh)

### 1. 系統深度分析與架構解構
此專案定位於「極端無網環境」下的應急通訊與物資調度，是一個高度依賴 **DTN (Delay-Tolerant Networking，延遲容忍網路)** 與 **MANET (Mobile Ad-hoc Network)** 技術的分散式系統。核心難點在於「無中央授權機制的狀態同步」與「實體世界不可靠連線下的資料交換」。

**App 技術框架**：Flutter（跨平台 iOS/Android 統一代碼庫）。

透過分析系統需求，我們將架構設計解構為以下四層：
1. **異質網路穿透 (Transport)**：採**頻段互補策略**與三層傳輸能力分級架構（手機端）。BLE 2.4GHz 負責手機間複雜資料互動（零門檻、手機內建）；Sub-1GHz 433MHz RF 負責接收傳統住警器火警訊號（穿透鋼筋混凝土樓板，向下相容既有設備，**部署於硬體骨幹節點，手機端不使用**）；LoRa 920MHz 負責骨幹遠距傳輸（Phase 2）。**手機端一律 BLE，不使用 Wi-Fi Aware (NAN) 或 AWDL**。手機 Tier 分級：Tier 1（iOS 前台 或 Android 掛 Foreground Service，電量 ≥ 40%）：全速 BLE 中繼，Data Mule 模式 / Tier 2（iOS 前台或 Android FS 但電量 20-40%，或 iOS 背景且電量 ≥ 20%）：降頻 BLE 中繼 / Tier 3（任何平台電量 < 20%）：僅 BLE 廣播自身 SOS。骨幹硬體節點（第三/四層）選配 433MHz RF 接收模組，可被動監聽市面連動型住警器訊號並轉譯為數位封包注入 Mesh 網路，實現「零汰換升級」。**(特此釐清：Android 無 CoreBluetooth 式背景 BLE 喚醒機制，要嘛掛 Foreground Service 全速跑，要嘛被系統殺掉；iOS 背景可受惠於 CoreBluetooth 喚醒機制維持 Tier 2 低頻中繼角色)**。
2. **多跳路由防洪 (Routing)**：疫情式路由 (Epidemic Routing) 搭配布隆過濾器 (Bloom Filter) 及 LRU Cache 去重，有效控制廣播風暴。
3. **無衝突狀態同步 (Application)**：借助 CRDT (無衝突複製資料型別) 處理併發修改。
4. **邊緣資料上鏈 (Synchronization)**：以 Store-and-Forward 機制將移動中的裝置視為流動物資車，遇網即上傳。

### 2. 災區社會心理學與實戰邊界優化 (Real-World Warfare & Limits Optimization)
為使系統從「好用工具」蛻變為「具備統治力的救援基礎設施」，我們針對「暗黑森林法則」與「極端物理邊界」導入了五大防護與韌性維度：

#### A. 信任機制與去中心化除權 (Trust Ladder & Decentralized Revocation)
極端斷網可能催生惡意行為，且被盜用的合法設備會成為毒瘤。
*   **漸進式 Trust Ladder（Level 0–3）**：身份驗證採不依賴政府合作即可運作的四等級架構。Level 0（匿名）Day 1 可用；Level 1（手機號 SMS OTP）由商業服務提供，完全在開發團隊掌控；Level 2（社群背書）純網內機制；Level 3（TW FidO 政府實名）以功能開關控制，合作達成前停用。所有等級共用同一 Ed25519 金鑰對，升級時就地提升 `identity_level` 欄位，不重新產生金鑰。UI 以灰/銅/銀/金盾牌徽章區分等級，供資源索取者快速辨識可信度。
*   **加權網內免疫隔離 (Weighted Quarantine Vote)**：當某設備捕捉到異常頻繁的干擾封包，可發出 `Quarantine_Vote`。每票依發票方 `identity_level` 計入不同權重（0.2 / 0.5 / 0.8 / 1.0），累計權重達 3.0 時自動封殺目標節點路由權，無須依賴中央伺服器。此機制可防止系統冷啟動早期（多數用戶為 Level 0）完全喪失免疫能力。

#### B. 網路封包的絕對優先權 (QoS & Triage)
Mesh 網路頻寬極其珍貴。
*   **路由霸權與檢傷 (Routing Preemption)**：將封包分級，收到 `SOS_RED` (瀕死邊緣) 封包將強制中斷所有一般物資傳輸，全頻寬保留給救命訊息，並觸發手機發出警報器引導。

#### C. 大數據分塊與重組機制 (Payload Chunking)
*   **突破 512 Bytes 限制**：面對傷患需傳送傷口照片或超長藥單的情境，底層實作 Chunking 將 Payload 分塊。接收端將碎片堆入暫存庫 (Reassembly Cache)，全數集齊驗證後才進一步廣播擴散。

#### D. 動態避險與時間軸修正 (Hazard Maps & Hybrid Logical Clocks)
*   **網狀圖層疊加 (Hazard Overlays)**：用戶長按離線地圖可擴散「路斷/化學外洩」警示，別人的地圖隨之疊加危險多邊形指路。
*   **HLC 時鐘防護 (Time Drift Prevention)**：解決斷電重啟造成的時間回到 1970 年問題！全面導入「混合邏輯時鐘」，附加遞增的計數器 (Logical Counter)，根絕絕對時間差導致的狀態合併崩潰。

#### E. 異質節點儲存力與物理降級容錯 (Storage Eviction & Fallback)
*   **超級節點騾子與資料驅逐 (Data Mules & Eviction)**：**Tier 1 手機節點（iOS 前台 或 Android 掛 Foreground Service，電量 ≥ 40%）**自動擔任 Data Mule 角色，全速 BLE 掃描並搬運離線日誌。電量跌破 40% 降為 Tier 2（降頻中繼）；跌破 20% 降為 Tier 3（僅自身 SOS）；充電回 60% 才再度升回 Tier 1（遲滯切換避免頻繁震盪）。**手機端 Data Mule 一律透過 BLE 傳輸，不使用 Wi-Fi Aware (NAN)**。應對爆炸資料量，導入冷熱資料驅逐閾值（500MB），優先刪除 INFO 封包而鎖存（PINNED）生命救援請求。離線地圖採 `flutter_map` + `flutter_map_mbtiles`（OSM MBTiles），採 App 內預先打包全台灣圖資策略 (.mbtiles Asset Bundle)，保障緊急時 100% 離線開箱即用。
*   **4 位數 PIN 盲操交割 (Physical Handshake Fallback)**：當面掃 QR Code 的常規方式若因停電無光、鏡頭損毀無法運作時，雙方靠近透過 BLE 交換資料後，觸發前端介面。供給方介面跳出 4 位數密碼，需求方跳出輸入框。具備防暴力破解保護：連續錯誤 3 次鎖定 30 秒；解鎖後若再連續錯誤 3 次，則強制取消物資配對（狀態回滾），物資釋放給其他索取者配對。
